PHP-SDK

So senden Sie Formulardaten Ihrer Webseite an das Backend. Das SDK signiert die Anfrage; das Backend versiegelt die Daten beim Eingang mit dem öffentlichen Schlüssel Ihres Kunden.

Wichtig: Das SDK verschlüsselt nicht selbst. Die Felder gehen im Klartext, geschützt durch HTTPS, an das Backend und werden dort sofort versiegelt. Verwenden Sie deshalb immer HTTPS (Klartext-HTTP akzeptiert das SDK nur für localhost). Details: Sicherheit.

Voraussetzungen

  • PHP 8.2 oder neuer mit den Erweiterungen sodium, curl, json und mbstring.
  • Ein veröffentlichtes Formular, der Datenschlüssel des Kunden und die SDK-Zugangsdaten (siehe unten). Das Formular muss aktiv sein.

1. Zugangsdaten erzeugen

Der Administrator des Backends erzeugt die Zugangsdaten einmal pro Formular über POST /tenants/{t}/forms/{f}/sdk-credentials (Admin-API; erfordert das Recht key.manage und eine frische Anmeldung). Die Antwort enthält die Formular-Kennung, den öffentlichen Kundenschlüssel und den privaten Signaturschlüssel. Letzterer wird nur in dieser einen Antwort angezeigt und nicht gespeichert.

  1. Antwort als credentials.json speichern, außerhalb des Web-Verzeichnisses Ihrer Anwendung.
  2. Zugriff beschränken: chmod 600 credentials.json und nur dem PHP-Benutzer zugänglich machen. Das SDK verweigert Dateien, die für Gruppe oder andere lesbar sind.
  3. Den Wert formId brauchen Sie später nicht im HTML; er steckt in der Datei.

2. SDK einbinden

Das SDK liegt im Repository unter sdk/php/ (Namespace FormBackend\, keine weiteren Abhängigkeiten). Kopieren Sie das Verzeichnis src/ in Ihr Projekt oder binden Sie sdk/php per Composer als Pfad-Repository ein.

3. Einsendung senden

<?php
require __DIR__ . '/vendor/autoload.php';

use FormBackend\Client;
use FormBackend\Credentials;
use FormBackend\Exception\RejectedException;
use FormBackend\Exception\TransportException;

$client = new Client('https://admin.example.org', Credentials::fromFile('/etc/meineapp/credentials.json'));

try {
    $submission = $client->submit([
        'name'       => $_POST['name'] ?? '',
        'nachricht'  => $_POST['nachricht'] ?? '',
        'interessen' => ['a', 'b'],
    ]);
    echo 'Danke! Referenz: ' . htmlspecialchars($submission->id);
} catch (RejectedException $e) {
    // Der Server hat abgelehnt (Status in $e->status)
} catch (TransportException $e) {
    // keine Antwort; siehe „Wiederholungen“
}

Regeln für die Felder

  • Werte sind Zeichenketten oder ganze Zahlen, auch in Arrays. Wahrheitswerte, Kommazahlen und null wandeln Sie bewusst selbst um; sonst gibt es eine InvalidInputException, bevor etwas gesendet wird.
  • Ungültiges UTF-8, leere Namen, mehr als 1000 Werte oder Verschachtelung über 64 Ebenen werden abgelehnt.
  • Oberste Feldnamen dürfen weder . noch Leerzeichen noch Klammern enthalten, weil PHP sie sonst stillschweigend umbenennt.
  • Dateien werden als Multipart unterstützt: drittes Argument von submit($fields, $key, $files). Felder und Dateiinhalt sind an die Signatur gebunden; Typ und Größe prüft das Backend.

Wiederholungen

Jeder Aufruf trägt einen Idempotency-Key (zufällig, wenn Sie keinen angeben). Bei Verbindungsfehlern und den Antworten 429, 502, 503, 504 wiederholt das SDK bis zu dreimal mit demselben Schlüssel, aber mit frischem Zeitstempel und frischer Signatur. Der Server liefert dann dieselbe Einsendung zurück, es entsteht nie eine doppelte.

Wenn Sie nach einem TransportException selbst wiederholen, übergeben Sie denselben Schlüssel: $client->submit($fields, $key). Derselbe Schlüssel mit anderem Inhalt wird mit 409 abgelehnt.

Fehler verstehen

SituationBedeutung
403Signatur abgelehnt: falscher Schlüssel, falsche Formular-Kennung oder Uhr weicht mehr als 5 Minuten ab (zuerst die Serveruhr per NTP prüfen). Nach einer Rotation gilt der alte Schlüssel noch 1 Stunde.
404Formular unbekannt oder noch nicht aktiv (es braucht ein veröffentlichtes Release).
409Idempotenz-Schlüssel bereits mit anderem Inhalt verwendet oder zugehörige Einsendung gelöscht; eine Löschung wird nicht durch erneutes Senden rückgängig gemacht.
413 / 415Zu groß / falscher Inhaltstyp.
429Zu viele Anfragen; $e->retryAfter nennt die Wartezeit in Sekunden.
503Das Formular ist noch nicht vollständig eingerichtet (z. B. fehlt der Kundenschlüssel) oder der Dienst ist nicht erreichbar.
TransportExceptionKeine Antwort nach drei Versuchen. Die Einsendung kann angekommen sein; mit demselben Schlüssel wiederholen.

Fehlermeldungen des SDK enthalten weder Feldwerte noch Schlüsselmaterial und können protokolliert werden.

SDK-Signaturschlüssel erneuern

Rufen Sie sdk-credentials erneut auf, erhalten Sie neue Zugangsdaten. Der bisherige Schlüssel bleibt 1 Stunde gültig, damit Sie die Datei auf allen Servern austauschen können; danach wird er abgelehnt. Bei Verdacht auf Abfluss rotieren Sie sofort (der Schlüssel erlaubt nur Einsendungen im Namen des Formulars, kein Lesen).

Kommandozeile

Zum Testen und für Skripte:

php sdk/php/bin/submit.php --credentials credentials.json --url https://admin.example.org \
    name=Beispiel nachricht=Hallo 'liste[]=a' 'liste[]=b'

Gibt die Einsendungs-Kennung aus. Exit-Codes: 0 gesendet, 1 abgelehnt, 2 Transportfehler, 64 Eingabe- oder Konfigurationsfehler.

Nachweise und Grenzen

Dokumentierte Einheitsprüfungen des SDK (Kanonisierung, Signatur, Wiederholungen, Fehlerabbildung, Absicherung der Zugangsdaten) sowie ein Test mit dem echten PHP-SDK gegen den echten Server mit Datenbank: Senden, Wiederholung mit gleichem Schlüssel, 409, 403, 404, nicht erreichbarer Server, und der Kunde entschlüsselt exakt, was gesendet wurde. Zusätzlich dokumentiert sind Multipart- und Browser-Downloadtests. In dieser Doku-Aktualisierung wurden diese Anwendungstests nicht erneut ausgeführt. Andere PHP-Versionen als 8.5 und Hosting-Umgebungen mit eingeschränktem cURL sind hier nicht belegt.

Datei-Uploads

Das dritte Argument ordnet Feldnamen entweder lesbare Dateipfade oder Objekte mit name und content (Dateibytes) zu; Listen erlauben mehrere Dateien je Feld. PHPs $_FILES-Struktur wird nicht direkt übernommen. Das SDK liest und signiert den Inhalt; der Server versiegelt Anhänge separat. Die Kommandozeile unterstützt --file. Erlaubte Typen, Anzahl und Größenlimits werden geprüft; ein Dateiupload ersetzt keine Schadsoftwareprüfung.

SDK-Selbstupdate per FTP/FTPS/SFTP

Das Backend kann das SDK aus seinem eigenen Image auf Kunden-Webspace installieren, aktualisieren und auf genau eine Vorversion zurückrollen (ADR 0011). Die Version stammt aus sdk/php/VERSION; es wird kein Paket aus dem Internet geladen.

  1. Systemadministration legt eine FTP-/SFTP-Verbindung an und weist sie dem Kunden zu. FTP nutzt explizites oder implizites TLS; Klartext-FTP ist nur im Entwicklungsmodus erlaubt. SFTP nutzt Passwortanmeldung und verlangt einen verifizierten Host-Key-Pin.
  2. Mit key.manage am Kunden und frischer Anmeldung ein Ziel je Formular anlegen: Verbindung, genaues Zielverzeichnis und autoUpdate:false. Zugangsdaten und Kundencode außerhalb des verwalteten SDK-Verzeichnisses halten.
  3. Installation manuell auslösen. Das Backend lädt in ein Nachbar-Stagingverzeichnis, liest Dateien zurück und vergleicht SHA-256. Erst danach wird umbenannt; .prev hält eine Vorversion. Rollback ist ein eigener ausdrücklicher Aufruf.

Normale Updates erlauben nur höhere SemVer-Versionen. Ein Host-Key-Wechsel wird abgelehnt; der über POST /connections/probe-sftp gelesene Fingerabdruck muss über einen unabhängigen Kanal geprüft werden. FTPS-Server mit erzwungener TLS-Sitzungswiederverwendung auf dem Datenkanal werden derzeit nicht unterstützt; SSH-Schlüsselanmeldung und automatische Testeinsendung nach Update fehlen.

Automatische Updates sind optional und standardmäßig aus. Wegen offener Reviewpunkte zu gemeinsamem physischem Ziel, Lauf-/Phasenpersistenz und Zeitlimits sind sie noch nicht freigegeben. Tests mit Fake-FTP und einem echten OpenSSH-Server belegen Teilpfade; daraus folgt keine Freigabe für beliebige Hoster oder Crash-/Konkurrenzfälle.

Die Erneuerung des SDK-Signaturschlüssels ist bereits vorhanden. Datenschlüsselrotation samt Hold-Rewrap ist dagegen noch nicht auf main.
