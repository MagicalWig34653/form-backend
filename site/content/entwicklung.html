Entwicklung

Für alle, die am Code mitarbeiten oder ihn selbst bauen möchten.

Voraussetzungen

  • Swift 6.x (Linux oder macOS), Docker (für Datenbanktests), Node.js 22+, PHP 8.2+ mit sodium, curl, json und mbstring (SDK und Krypto-Kreuztests).

Backend

# Tests ohne Datenbank, plus PHP-Kreuztest (macOS: nativer Build-Modus wegen Codesign)
sh backend/run-tests.sh

php sdk/php/tests/sdk_test.php

# alle Tests inkl. Datenbank (startet und entfernt eine MariaDB auf 127.0.0.1)
P3B_PORT=33417 bash backend/integration-test.sh

# Linux-Lauf in Docker (MariaDB + Swift im privaten Netz)
bash backend/ci-linux.sh

# echter Server: Migration, Start, Anmeldung, Schlüsseldatei-Prüfung
P3B_PORT=33417 bash backend/smoke-admin.sh

# Ende-zu-Ende: Chromium mit virtuellem Authenticator gegen den echten Server
P3B_PORT=33417 bash backend/e2e-login.sh

Die Datenbanktests legen je Test eine eigene Datenbank an und arbeiten nur mit synthetischen Daten. Führen Sie nie zwei Datenbankskripte gleichzeitig aus (gleicher Containername und Port).

Oberfläche

cd pwa
npm ci
npm run lint && npm run check && npm test
npm run build
npx playwright install chromium
npx playwright test

Diese Dokumentation

node site/build.mjs            # baut site/dist/ ohne --base
node site/check.mjs            # prüft Metadaten, Links und Anker
python3 -m http.server -d site/dist 8000

Der Bau braucht keine Abhängigkeiten. Inhalte liegen als HTML-Fragmente in site/content/.

Arbeitsweise

  • Verträge zuerst: Schnittstellen und Datenmodell stehen unter contracts/; offene Fragen werden nicht als Beschlüsse umgesetzt.
  • Entscheidungen mit Begründung stehen als ADR unter docs/decisions/.
  • Tests nach Risiko: Rechte, Verschlüsselung, Wiederholungen und Migration werden mit echten Verhaltenstests gegen die Datenbank geprüft, nicht nur mit Einzeltests.
  • Das Repository ist das Gedächtnis: Stand, Prüfergebnisse und nächste Schritte stehen in docs/STATUS.md und docs/FORTSETZUNG.md.
  • Code und Kommentare englisch, Texte für Nutzer deutsch.

Continuous Integration

Jeder Push startet: Linux-Tests auf amd64 und arm64 (mit MariaDB), Oberflächen-Prüfungen (Lint, Typen, Unit, Build, Browsertests mit Barrierefreiheitsprüfung, Abhängigkeits-Audit) und den Bau des Docker-Images für beide Architekturen. Auf main wird das Image in die GitHub Container Registry veröffentlicht, diese Dokumentation auf GitHub Pages.

Stand und gezielte Prüfungen (03.11.2026)

Auf main vorhanden: Datenschutzfunktionen (ADR 0012), Domains/Ereignisstatistik (0015), Webhooks (0013), externe Speicher (0019) und SDK-Selbstupdate (0011). Datenschutz-, Domain-, Webhook- und Storage-Tests prüfen die jeweiligen Fehler- und Rechtepfade. Ein Beschluss oder bestandener Build allein ist kein Laufzeitnachweis.

# Datenbankläufe ausschließlich seriell; jeweils eigenen Container/Port verwenden
P3B_PORT=33420 P3B_NAME=domains-mariadb ./backend/integration-test.sh --filter Domain
P3B_PORT=33418 P3B_NAME=webhooks-mariadb ./backend/integration-test.sh --filter Webhook
# Gesamtkette Registrierung, SDK, Upload und Browserentschlüsselung:
bash backend/e2e-setup.sh
# SFTP gegen echten Testserver:
bash backend/sftp-test.sh
# Betriebsdateien und Kommando-Doubles:
python3 scripts/check-deploy.py

Die Skriptprüfung umfasst Konfiguration und simulierte Aufrufreihenfolge, keinen realen Swarm-/Proxy-/Restore-Lauf. Die aktuelle Speicherbaseline hat 74 Tabellen; ein Bestandsupgrade ist noch nicht unterstützt. Nie einen Produktionsbestand für Tests zurücksetzen.

Rotation, Engine, MCP und Altdatenmigration sind noch nicht auf main. Die Zahl vorhandener Tests ist kein Sicherheitsurteil; übersprungene Fälle, blockierte Docker-/Socketläufe und fehlende Browsermatrix müssen im Prüfbericht stehen. Der zuletzt dokumentierte CI-Gesamtlauf war wegen eines instabilen Deploy-Tests rot; eine Korrektur ist eingespielt, ein neuer Erfolg wird hier nicht behauptet.
