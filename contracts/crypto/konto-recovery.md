# Konto-Recovery und automatische Sicherheitsaktualisierung (P12-B)

03.11.2026. SPDX: AGPL-3.0-only. Ergänzung zu `schluessel.md`, ADR 0016/0024.

- `GET /admin/api/v1/me/key-bundle` enthält zusätzlich `recovery: null | {revision, salt, iterations, iv, wrap}`. Cookieauthentifiziert, budgetiert, no-store; nur das eigene Konto. Keine unautorisierte öffentliche Recoveryabfrage.
- `PUT /admin/api/v1/me/account-recovery`: `{publicKey, expectedRevision: null | string, recovery: {salt, iterations, iv, wrap}}`. Cookie, CSRF, Origin, Budget, frische menschliche Sitzung. base64url: Public Key 32 Byte nutzbares X25519, Salz 32, IV 12, Hülle 48; Iterationen exakt 600000. Initiale Anlage oder Ergänzung eines identischen vorhandenen Kontoschlüssels. Abweichende Identität/Revision → 409. Kontozeile und Kontoschlüssel unter Sperre, Hülle + Audit atomar. Antwort 200 `{revision}` mit no-store. Keine Klartextcodes, privaten Schlüssel oder Codehashes. Browser bestätigt den Code vor dem PUT; Codeprüfung erfolgt ausschließlich lokal durch Entschlüsselung und Identitätsabgleich.
- `GET .../tenants/:id/key-rotation` liefert zusätzlich `requested: boolean`. Der Bedarf überlebt Browser-/Serverneustarts; bei vorhandenem retiring zunächst diesen Bestand abschließen. Danach gegebenenfalls nächste Rotation.
- `POST .../key-rotation` akzeptiert zusätzlich `automatic?: boolean`, Zugangseinträge zusätzlich `expectedPublicKey?: string`. Automatisch: vollständige Menge aktiver weiterhin berechtigter Altzugangskonten, erwarteter Public Key für jeden Eintrag verpflichtend. Fehlende/zusätzliche/zwischenzeitlich geänderte Empfänger → 409; keine stillen neuen Freigaben. Bestehende Frische-/key.manage-/Eigenzugangs-/Migrationsprüfungen bleiben. Markierung wird erst in derselben Transaktion wie Beginn entfernt. Rewrap und Abschluss unverändert ADR 0016.

Assistentenvertrag: `pwa/src/lib/crypto/RecoveryStep.svelte`, Props `oncomplete?: () => void`, `security?: boolean`. Der Assistent darf Schritt 2 nach `oncomplete` nur mit `keyring.unlocked && !keyring.recoveryRequired` verlassen. Vorhandene gesicherte Recovery kann über den Code geöffnet oder mit einem bereits entsperrten Konto bestätigt werden. Weitere Assistentenschritte bleiben P11-CD.

Bestandsupgrade: Baseline unverändert, getrenntes `backend/db/upgrades/0027-account-recovery.sql` (Migrationsname `0027-account-recovery`); eingebunden in App-Migrate und AdminFixture. Nicht produktiv ausgeführt. Alte Einzelcodes bleiben ausschließlich gezielte Bestands-Recovery; keine behauptete Wiederherstellung ohne eine vorhandene Quelle. Kontorecovery ist keine Umgehung von Authentifizierung, Entzug oder Vertrauensprüfung. Neue Fremdzugänge benötigen weiter explizite Identitätsbestätigung.
